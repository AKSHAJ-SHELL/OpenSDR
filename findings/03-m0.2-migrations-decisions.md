## M0.2 — Alembic migrations: decisions & notes

**Status:** implemented on branch `m0.1-auth`; tests green (93 passed, 0 skipped, Postgres up).
**Plan:** `plans/m0.2-migrations.md`. **Closes:** finding D1.

### What shipped
- Alembic introduced: `alembic.ini` (root) + `craftsman/migrations/` (inside the package so
  it ships in the Docker image). `env.py` reads the DB URL from the app's `Settings` and
  targets `Base.metadata` — one source of truth — with `compare_type` / `compare_server_default`.
- Baseline `0001_baseline` autogenerated from the live models (all 14 tables incl. M0.1's
  `api_keys`), then hand-finished for two autogenerate blind spots: the `import pgvector`
  line and a `CREATE EXTENSION IF NOT EXISTS vector` before the Vector-column tables.
- `run_migrations()` in `craftsman/core/db.py` runs `alembic upgrade head`. The API lifespan
  and the `create_key` bootstrap call it. `init_db()`/`create_all` stays as the dev/test/demo
  path only (tests and seed scripts call it directly).
- `alembic.ini` uses `script_location = %(here)s/craftsman/migrations` so migrations resolve
  regardless of the current working directory (verified by running `run_migrations()` from `/tmp`).
- Dockerfile now copies `alembic.ini` into the image.
- Tests (`tests/e2e/test_migrations.py`): upgrade→head builds the expected schema, downgrade
  base → re-upgrade round-trips, and a **no-drift guard** (`alembic check`) that fails if a
  model changes without a matching migration.
- CI added (`.github/workflows/ci.yml`): Postgres+pgvector service, install, `pytest` — which
  runs the migration round-trip on a fresh DB. Comments written to be human-readable.

### Decisions the human approved (2026-07-21)
1. Add `alembic` as a runtime dependency (edits `pyproject.toml`, needs `pip install`).
2. Run migrations in the API lifespan (preserves one-command deploy; caveat below).
3. Add the GitHub Actions CI workflow now, with readable comments.

### Notes / caveats for the gate
- **Lifespan migration + multiple API replicas:** running `upgrade head` inline is fine for
  the single-node default. At multi-replica scale, move it to a one-shot migrate job so
  replicas don't race the same DDL. Documented in `db.py` and the plan.
- **Downgrade does not drop the `vector` extension** — dropping a shared extension is unsafe;
  downgrade only removes the app tables.
- **Two schema-build paths coexist by design:** migrations (prod, via `run_migrations()`) and
  `create_all` (dev/test/demo, via `init_db()`). The no-drift test guarantees they agree.

### Verification receipts
- Fresh empty DB (no extension) → `alembic upgrade head` → 14 tables incl. `api_keys`;
  `downgrade base` → 0 app tables; re-`upgrade head` → clean.
- `alembic check` → "No new upgrade operations detected" (models == migration).
- API started against a fresh empty DB → lifespan migrated it (health 200, 14 tables).
- `run_migrations()` run from `/tmp` → succeeded (CWD-independent).
