# Plan — Epic M1.3: Lead & review operations UI (E2)

**Branch:** `m1.1-campaign-builder` (M1 line, stacked on `m0.1-auth`) · **Status:** implemented · **Roadmap:** M1.3

## Goal

Two surfaces that exist server-side but have no operator UI: lead operations (import,
filter, suppress, erase, understand the score) and the review queue (blocked copy with
validator errors + the M0.6b retry/skip/kill actions; low-confidence classifications with
approve/override). Pure surfacing, plus the small API gaps that make surfacing possible.

## Current state (verified in code)

- **Review queue is fetched but never actionable.** `api.review()` is called once on the
  overview page (`web/src/app/page.tsx:20`) for an attention list. There is no review page.
  `POST /inbox/review/{id}/action` (retry/skip/kill) and `POST /inbox/{msg_id}/reclassify`
  both work and have **zero UI**.
- **`GET /inbox/review` omits `message_id`** (`inbox.py:71-79`) — it returns id, kind,
  enrollment_id, payload, created_at. Classification items are keyed to a message, so the
  UI literally cannot call reclassify on them. This is the same defect M0.6b fixed for
  `enrollment_id`, one field over. It also returns untyped `list[dict]` and carries no
  lead/campaign context, so a reviewer sees a payload blob with no idea who it's about.
- **Two item kinds:** `classification` (payload: label, confidence, from) from
  `inbox/pipeline.py:74`, and `copywriter` (payload: errors, slots) from `tasks.py:148`.
- **No manual suppress endpoint.** `suppress()` exists in `compliance/suppression.py:35`
  but nothing exposes it. Only erase (admin, destructive) is reachable.
- **Erase requires `admin`; the dashboard key is `read operate`** (README quickstart mints
  `--scopes read operate`). An erase button wired naively 403s for every standard install.
- **`GET /leads` already filters** by `status`, `score_gte`, `limit` — needs only UI.
- **CSV import** is `POST /leads/import`, multipart. `api.ts` has JSON-only helpers; the
  proxy already streams the raw body and forwards content-type, so multipart passes through
  provided we do *not* set Content-Type ourselves (the browser must set the boundary).
- **The score cannot be honestly explained from what's stored.** `icp_score`
  (`scoring/icp.py:40`) = `0.7·sim01 + 0.3·rule_score(title)`. Only the final float is
  persisted — components are computed transiently in `activate` and discarded. Worse:
  a lead is re-scored by *every* campaign activation, so `lead.icp_score` means "score
  against whichever campaign was activated last", and **we don't record which campaign**.
  A popover claiming "cosine vs your ICP" without naming the ICP would be guessing.

## Design

### Phase 1 — API gaps (the UI cannot be built without these)

- **`GET /inbox/review` → typed `ReviewItemOut`**: existing fields **+ `message_id`** (the
  blocker) + context resolved by join: `lead_email`, `lead_name`, `campaign_name`,
  `enrollment_state`. Additive; the overview page's use is unaffected.
- **`POST /leads/{id}/suppress`** (`operate`, 204): manual do-not-contact via the existing
  `suppress(db, email, reason="manual")`. Distinct from erase — suppression keeps the row
  and is the reversible-ish operational action; erase is the GDPR hammer.
- **Score provenance** (per open question 1, recommended option): migration `0006` adds
  `leads.icp_cosine`, `leads.icp_rule`, `leads.icp_scored_campaign_id` (FK, nullable),
  `leads.icp_scored_at`. `icp_score()` gains a sibling returning the breakdown.
  **Only `campaigns.activate` persists it** — `run_dry_run` scores in memory by design and
  must keep writing nothing to the lead (M1.2 guarantee, asserted in `test_dry_run.py`).
  Old rows have NULL components → the popover says "scored before component tracking"
  rather than inventing numbers.

### Phase 2 — Leads page (`web/src/app/leads/page.tsx`)

- **Import**: file picker + drag target posting multipart to `/leads/import`; renders the
  `ImportResult` (imported / deduped / suppressed / errors) inline. New `upload` helper in
  `api.ts` that omits Content-Type.
- **Filters**: status select + min-score input + limit, driven through the existing query
  params via server-side `searchParams` (keeps the page a server component, URL shareable).
- **Row actions**: Suppress (confirm) and Erase (typed-confirmation dialog, since it is
  irreversible). Erase surfaces a specific message on 403 explaining the dashboard key
  lacks `admin` by design — see open question 2.
- **Score popover**: click the score bar → breakdown (cosine component × 0.7, rule
  component × 0.3, the matched seniority keyword, the campaign whose ICP was used, when).

### Phase 3 — Review page (`/review`, new; sidebar entry)

- Two sections, one per kind, from the enriched endpoint:
  - **Blocked copy** (`copywriter`): lead + campaign context, the rejected slot fills, and
    the validator errors verbatim, with **retry / skip / kill** buttons wired to the M0.6b
    action endpoint. Each button states its consequence ("retry re-runs research + copy",
    "skip advances past this step", "kill leaves it terminal").
  - **Low-confidence classifications** (`classification`): the reply text, the model's
    label + confidence, an **Approve** button (resolve as-is) and override buttons wired to
    `reclassify` — which is the same call the inbox already makes, so downstream effects
    stay identical. Approve resolves the item via the action endpoint with `skip` semantics
    only if it has an enrollment; otherwise it just resolves (see open question 3).
- Overview page's "needs attention" tile links here.

### Phase 4 — Tests

- **API (pytest):** review response includes `message_id` + context for both kinds; suppress
  endpoint suppresses + flips lead status, is idempotent, requires `operate`, 404s unknown;
  erase still requires `admin`; score components persist on activate and dry-run and survive
  a re-score; filters unchanged. Full suite stays green, 0 skipped.
- **UI:** browser QA of both pages against a current-code stack (no JS test infra exists;
  adding it is an ask-first `package.json` change — flagged again in §Concerns).

## Open questions (⛔ decide before implementation)

1. **Score explanation data.** Recommend **store components** (migration 0006): honest
   across the M2.3 weight change (0.7/0.3 → 0.6/0.25/0.15) and can name the campaign whose
   ICP was used. Alternative — derive by inverting the formula (`sim01 = (score − 0.3·rule)/0.7`):
   zero migration and always sums back to the displayed number, but silently misattributes
   once weights change and can never say which campaign scored the lead.
2. **Erase in the dashboard.** Recommend **render it, fail loudly**: the button exists, and
   a 403 explains that the dashboard key is `read operate` by design and in-UI erase needs
   an admin key. Alternatives: hide erase from the UI entirely (docs-only curl), or tell
   users to give the dashboard an admin key (widens blast radius of a stolen dashboard key).
3. **"Approve" semantics for a low-confidence classification.** Recommend: approve =
   resolve the queue item *and* re-apply the label at confidence 1.0 through `reclassify`,
   so the downstream state change that was skipped at low confidence actually happens.
   Alternative: approve = mark resolved only, leaving the enrollment untouched.
