# Plan — Epic M1.2: Dry-run / preflight mode (E4)

**Branch:** `m1.1-campaign-builder` (M1 line, stacked on `m0.1-auth`) · **Status:** implemented (decisions: synthetic dry-run@localhost sender; UI-only activate gate; n ≤ 10 as spend guard; dry-run reads nested under /campaigns/{id}/dry-runs) · **Roadmap:** M1.2

## Goal

"Interview your next hire": before a campaign goes live, route the real pipeline —
research → bandit pick → slot-fill → validate → build → send — for N sample leads, with
the send forced to Mailpit regardless of configured SMTP. The dashboard shows rendered
emails and validator verdicts side by side; Activate becomes two-step (dry-run first,
skippable with an explicit override).

## Current state (verified in code)

- The production path lives in `generate_and_send` (`workers/tasks.py:70`) and is
  entangled with state I must NOT touch in a preview: enrollment state machine, campaign
  slot reservation, `mailbox.sent_today`, Message claim rows, and threading lookups.
- `research_company` (`research/agent.py:25`) caches the brief on the Company row
  (30-day cache). A dry-run doing real research warms exactly the cache production would
  use — acceptable and useful, not a leak.
- `generate_copy` (`copywriter/fill.py`) is pure: LLM call + validator, no DB writes.
  `pick_arm` is pure sampling; posteriors update only in `settle`, so a dry-run pick
  mutates nothing.
- `build_email` (`sender/smtp.py:112`) mints a **real unsubscribe token row** via
  `make_unsubscribe_token` — a dry-run must not write those.
- `deliver` sends wherever `mailbox.smtp_host` points. Mailpit's SMTP is
  `localhost:1025` (compose: `mailpit:1025`); config has `mailpit_url` (HTTP UI) but no
  Mailpit SMTP setting.
- Migrations head is `0004`; erasure cascade is `compliance/suppression.py:erase_lead`
  — any new store holding lead PII must join it (M0.4 guarantee).

## Design

### Phase 1 — Schema + config

- Migration `0005`: `dry_runs` (id, campaign_id FK, status `running|complete|failed`,
  requested_n, error NULL, created_at, finished_at NULL) and `dry_run_items`
  (id, dry_run_id FK, **lead_id FK**, lead_email, lead_name, icp_score, variant_id,
  variant_name, subject, body, validator_ok, validator_errors JSONB, delivered bool,
  error NULL). Separate items table (not JSONB) so erasure is a plain DELETE.
- **Erasure:** `erase_lead` gains `dry_run_items` (delete by lead_id); adversarial
  erasure test extends to assert zero dry-run rows survive.
- New knobs (documented in `APPLICATION_OVERVIEW.md` §10): `mailpit_smtp_host`
  (default `localhost`), `mailpit_smtp_port` (default `1025`); compose passes
  `MAILPIT_SMTP_HOST=mailpit`.

### Phase 2 — Worker task + endpoints

- `POST /campaigns/{id}/dry-run` (`operate`) body `{n: int = 3}` (1 ≤ n ≤ 10): 404 unknown
  campaign, 400 if no active variants on step 1 (mirror of activate's guard), else create
  `dry_runs` row → enqueue `run_dry_run` (Celery, `research` queue) → 202 `{id}`.
- `GET /campaigns/{id}/dry-runs` (`read`): recent runs, newest first.
  `GET /dry-runs/{id}` (`read`): status + items.
- `run_dry_run` task, per the roadmap "full pipeline, Mailpit only":
  - **Sample selection:** verified, unsuppressed leads; score in memory against the
    campaign ICP exactly like activate does but **persist nothing** (no `icp_score`, no
    `disqualified`); take top-N by score, flagging any below `icp_threshold` in the item
    (`icp_score` shown; UI badges below-threshold).
  - Per lead: `research_company` (cache-warm, real fetch through the SSRF guard) →
    `pick_arm` over step-1 active variants → `generate_copy` → item row records verdict
    and slots/copy whether it passed or failed. Validator failure is a **successful
    dry-run outcome** (that's the point) — shown, not retried into the review queue.
  - Passing fills get a compliance-shaped email (same footer/headers) with a
    **placeholder unsubscribe URL** (no token row) + `X-Craftsman-Dry-Run: 1` header,
    delivered to `mailpit_smtp_host:port` from a synthetic `dry-run@<campaign-mailbox
    domain or localhost>` — `run_presend_checks`, slot reservation, `sent_today`, and
    Message rows are all bypassed by construction (this code path never touches them).
  - Per-lead failure (research error, LLM error, SMTP-to-Mailpit down) is captured on
    the item; the run completes with whatever it got. Step 1 only (later steps are
    threaded replies; previewing them without a thread would fake data).

### Phase 3 — Dashboard

- Builder page (`/campaigns/[id]`): "Dry run" panel — run button (N selector), poll the
  run until complete, then per-lead cards: name/email, ICP score (badged if below
  threshold), chosen variant, PASS/FAIL with validator errors inline, and the rendered
  subject + body; link to the Mailpit UI (`mailpit_url`, exposed via a tiny
  `GET /meta` addition or reuse of an existing config surface — resolved at
  implementation, `read`-scoped either way).
- **Two-step activate:** Activate button first checks for a completed dry-run for this
  campaign; none → confirmation dialog: "No dry-run yet — run one (recommended) or
  activate anyway". Explicit override proceeds. Enforcement is UI-level (see open
  question 2).

### Phase 4 — Tests (e2e, mock LLM; SMTP captured by monkeypatching `aiosmtplib.send`)

- Dry-run creates zero Messages, zero UnsubscribeTokens, no enrollment/state changes,
  `sent_today` untouched on campaign and mailboxes, variant α/β unchanged, lead
  `icp_score`/status not persisted.
- Delivery kwargs assert `mailpit_smtp_host:port` even when mailboxes have real SMTP
  config; dry-run email carries the `X-Craftsman-Dry-Run` header and placeholder unsub.
- Suppressed leads never selected; below-threshold leads flagged; validator-rejecting
  skeleton produces a FAIL item with errors and no delivery; per-lead research failure
  doesn't kill the run; n bounds 422.
- Erasure test: lead with dry-run items → erase → zero rows.
- Scope: POST requires `operate`, GETs require `read` (fail-closed walk covers 401s).

## Open questions (⛔ decide before implementation)

1. **Sender identity for the Mailpit message.** Recommend synthetic
   `dry-run@localhost` From (no mailbox selection, no warmup interaction). Alternative:
   pick the campaign's real mailbox for a faithful From header — touches
   `pick_mailbox` and implies capacity semantics that don't apply.
2. **Server-side activate gating.** Recommend UI-only for v1 (API stays scriptable;
   the override is explicit in the UI). Alternative: `POST /activate` 409s without a
   completed dry-run unless `?force=true` — stricter, but breaks existing API users
   and tests.
3. **LLM spend guard.** Dry-run with a real provider costs ~2 LLM calls/lead. n ≤ 10
   cap + operate scope: sufficient? Or an explicit config knob to disable dry-run?
   Recommend: cap is sufficient, no knob.
