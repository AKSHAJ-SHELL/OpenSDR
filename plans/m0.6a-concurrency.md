# Plan — Epic M0.6a: Concurrency & reproducibility (B2 + B3)

**Branch:** `m0.1-auth` (M0 line) · **Status:** awaiting approval · **Roadmap:** M0.6 (split; 0.6a = correctness, 0.6b = observability) · **Findings:** B2, B3

## Goal

Two send-path correctness bugs, plus a reproducibility knob:
- **B3a — per-campaign cap races.** 4 workers can each pass a cap check that should fail
  collectively → the campaign over-sends. Make it an **atomic reserve**.
- **B3b — send is not idempotent.** With `acks_late=True`, a worker killed after
  `deliver()` but before commit gets the task redelivered and **sends a second email**.
  Make the dedupe claim happen **before** dispatch.
- **B2 — unseeded bandit RNG.** Add an opt-in `BANDIT_SEED` for reproducible sims/CI;
  unset = today's behavior.

## Current state (verified in code)

- `sender/smtp.py:74` `run_presend_checks`: `campaign_sent_today()` **counts Message rows**
  then compares to `daily_cap` — classic read-then-act. Under concurrency N workers all
  read 49/50, all pass, all send. No row lock, no atomic increment.
- `tasks.py:generate_and_send` (`acks_late=True`, `max_retries=3`): `deliver()` at line
  166, then the outbound `Message` is inserted at 170 and state advances at 187, all
  committed at `session_scope` exit. A crash between 166 and commit → Celery redelivers →
  enrollment still `ready` → **re-sends**. No idempotency key anywhere.
- `messages` has **no step column** and **no uniqueness** on outbound; nothing prevents
  two outbound rows for the same (enrollment, step).
- `bandit/thompson.py:pick_arm(arms, rng=None)` already accepts an rng; `tasks.py:113`
  passes a fresh unseeded `np.random.default_rng()` each send.
- Per-mailbox spacing is already a **Redis token bucket** (`limiter.py`) — correct across
  workers. This plan does **not** touch it (B3's spacing sub-item is already sound; I'll
  add a test that documents the mechanism, per §3.3).
- `reset_daily_counters` (`tasks.py:253`) already resets `mailbox.sent_today` daily — the
  natural home to also reset a campaign counter.

## Design

### Migration `0002` (uses the Alembic machinery from M0.2)

1. `campaigns.sent_today INTEGER NOT NULL DEFAULT 0` — the atomic cap counter.
2. `messages.step_order INTEGER NULL` — which sequence step an outbound row is for.
3. Partial unique index `uq_outbound_step` on `messages(enrollment_id, step_order)`
   `WHERE direction = 'outbound'` — the idempotency guarantee at the DB level.

### B3a — atomic per-campaign cap (reserve / release)

Replace the count-and-compare with a conditional atomic update, evaluated **last** in the
pre-send order (after suppression/mailbox/rate-limit) so a slot is only reserved when a
send is actually imminent:

```sql
UPDATE campaigns SET sent_today = sent_today + 1
WHERE id = :cid AND sent_today < daily_cap
RETURNING id
```

- Row returned → slot reserved (the row lock serializes concurrent workers; no two can
  both cross the cap). No row → cap reached → `SendBlocked("campaign_daily_cap")`.
- **Release on failure:** if anything after the reserve fails (deliver raises, etc.),
  decrement `sent_today` in the except path so a transient failure doesn't burn a slot.
- `reset_daily_counters` also zeroes `campaigns.sent_today`.
- `campaign_sent_today()` (count of messages) stays for analytics/back-compat but is no
  longer the gate.

### B3b — send idempotency (claim before dispatch)

Restructure `generate_and_send` so the **claim is committed before `deliver()`**:

1. generate + validate copy (unchanged)
2. run pre-send checks incl. the atomic cap reserve → mailbox
3. **claim:** `INSERT` the outbound `Message` for `(enrollment_id, step_order)` in a
   `sending` state (subject/body set, `smtp_message_id=NULL`, `sent_at=NULL`), then
   **commit the claim**. On `IntegrityError` (the partial unique index) → this step was
   already claimed by a prior attempt → **skip the send** (return; do not re-deliver).
4. `deliver()`
5. finalize: set `smtp_message_id`, `sent_at`, `bandit_outcome='pending'`,
   `outcome_deadline`; advance state; schedule next step; commit.

**Tradeoff (explicit):** this is *never-double, may-rarely-skip*. If a worker dies between
the claim commit (3) and deliver (4), the retry sees the claim and does **not** re-send —
so that one email is lost rather than duplicated. For cold outbound a missed send is far
cheaper than a double send (duplicates burn domain reputation and look like a bot). True
exactly-once is impossible over SMTP; no-duplicates is the correct target. A follow-up
could re-drive genuinely-unsent claims (rows with `sent_at IS NULL` older than N min) —
noted for 0.6b's re-drive work, not built here.

### B2 — seedable bandit RNG

- `Settings.bandit_seed: int | None = None` (env `BANDIT_SEED`).
- `bandit/thompson.py`: `get_bandit_rng()` returns a **cached, seeded** generator when the
  seed is set (a deterministic *stream* across calls — not a fresh identical draw each
  time), else a fresh `default_rng()` per call (today's behavior). `generate_and_send`
  and the simulator call `get_bandit_rng()`.
- Documented as a **sim/CI reproducibility** knob: in multi-worker prod each process would
  seed identically and lose independence, so leave it unset there. Added to the knobs table.

## Tests

**Concurrency (`tests/adversarial/test_send_concurrency.py`, real Postgres):**
1. **Cap under true concurrency** — N threads (own session each) call the atomic reserve
   against one campaign with `daily_cap = k < N`; assert exactly `k` reservations succeed,
   `N-k` get `campaign_daily_cap`, and `campaigns.sent_today == k`. This is the read-then-
   act race, tested with real row locking.
2. **Reserve/release** — reserve, then simulate a downstream failure → release → count
   returns to prior; the freed slot is reusable.

**Idempotency (`tests/e2e/test_send_idempotency.py`, real Postgres, mock SMTP):**
3. **Double-dispatch → one email** — run the send path for an enrollment/step twice
   (simulating an `acks_late` redelivery); assert exactly **one** outbound Message and
   **one** `deliver` call (deliver monkeypatched to count).
4. **Crash-after-deliver, before finalize** — force the finalize step to raise after a
   counted deliver; re-run the task; assert **no second deliver** and the claim row is
   present. Documents the never-double property.
5. **Suppression race** — suppress the lead between generation and the send-time check;
   assert the send is blocked (the check already queries live state — characterized).

**Spacing mechanism (§3.3 documentation test):** a test that asserts `acquire_send_slot`
is enforced via Redis (cross-worker), not in-memory — so the green result isn't luck.

**Bandit RNG (`tests/unit/test_bandit_seed.py`):** with `BANDIT_SEED` set, two runs of a
pick sequence match; unset, `get_bandit_rng()` returns independent generators.

Existing bandit/scheduling/integration tests must pass unmodified. Suite green, 0 skipped.

## Open questions for approval

1. **Idempotency tradeoff = never-double, may-rarely-skip** (claim-before-deliver, skip on
   existing claim). Confirm no-duplicates is the priority over never-miss. I propose yes.
2. **Cap via DB counter column** (`campaigns.sent_today`, atomic UPDATE…RETURNING) vs. a
   Redis INCR counter. I propose the DB column — single source of truth, uses our Alembic,
   survives Redis flushes. Redis is faster but splits truth.
3. **Concurrency tested at the mechanism level** (threads hitting the atomic UPDATE; task
   re-invocation for idempotency) rather than by spinning real `--concurrency=4` Celery
   workers in CI (flaky, slow). I propose mechanism-level tests + a note that full
   multi-worker load is a manual/ops check. Confirm.
