# Plan — Epic M2.1: Enrichment framework (revive the orphans)

**Branch:** `m2.1-enrichment-framework` (off `main` = M0 + M1) · **Status:** implemented · **Roadmap:** M2.1 (`ROADMAP.md:162`)

> Implementation deltas from the plan, all in the spirit of the repo's doctrine:
> (1) the `lead_enrichments` FK does **not** cascade — M0.4 decided constraints block
> accidental lead deletion and only `erase_lead` deletes; the erasure path deletes
> provenance rows explicitly (tested). (2) `Lead.seniority` was added as a canonical
> column (the roadmap names seniority as an enrichment output; the plan's column list
> omitted it). (3) `first_name`/`last_name` joined the canonical fields — providers
> return them and the anti-clobber rule protects CSV values. (4) `adapters.py` was
> folded into `enrichment.py` (the plan allowed either) and the orphaned
> `LeadEnrichment` schema removed with it.

## Goal

Turn the dead `ingest/adapters.py` into a real, chainable **enrichment framework** with
per-field provenance, and wire it into the pipeline so a verified lead gets its title,
seniority, company facts, LinkedIn, and phone filled from **bring-your-own-key** providers
(Apollo, Hunter) — never from a pretend proprietary database. Two invariants hold: (1) a
dead or slow provider **never blocks email verification**, and (2) enrichment **never
silently clobbers operator-supplied data** (a value the CSV gave us outranks a provider
guess). This is the foundation M2.2 (sourcing) and M2.3 (intent) build on.

## Design

### 1. `EnrichmentResult` + `EnrichmentProvider` protocol — `craftsman/ingest/enrichment.py` (new)

Promote the adapter Protocol to a provider that takes a **lead-shaped input** and returns a
normalized result carrying source + confidence, so the chain can reason about precedence:

```python
@dataclass(frozen=True)
class EnrichmentResult:
    source: str                 # "apollo" | "hunter" | "null"
    confidence: float           # 0..1, provider-reported or a fixed default
    fields: dict[str, str]      # only keys the provider actually returned, non-empty
    # canonical field keys: title, seniority, phone, linkedin_url,
    #   company_name, company_domain, company_industry, company_size, company_description

class EnrichmentProvider(Protocol):
    name: str
    async def enrich(self, lead: EnrichmentInput) -> EnrichmentResult | None: ...
```

`EnrichmentInput` is a tiny frozen struct (`email`, `company_domain`) so providers never
touch the ORM. `ApolloProvider` / `HunterProvider` **wrap the existing httpx calls from
`adapters.py`** (same endpoints, same parsing) and map into `EnrichmentResult.fields`,
dropping empty values. A `NullProvider` returns `None` (the honest "enrichment disabled"
path). The raw HTTP call stays behind one `async _fetch(...)` seam per provider so tests
patch it with recorded fixtures — no network.

`adapters.py` is **kept as the thin HTTP layer** (or folded in); no behavior of the HTTP
calls changes, only who calls them.

### 2. Provider chain with per-field precedence — `chain_enrich(...)` in `enrichment.py`

```python
async def chain_enrich(providers: list[EnrichmentProvider], inp) -> tuple[dict, list[Prov]]
```

- Runs providers **in configured precedence order**. Each provider is wrapped in
  try/except: a raise / timeout / HTTP error / malformed body is logged and **skipped**,
  never propagated — one dead provider can't sink the chain (and enrichment runs *after*
  verify, so it can't sink verification either).
- **Per-field first-writer-wins in precedence order:** for each canonical field, the first
  provider that returned a non-empty value owns it. Returns `(merged_fields, provenance)`
  where `provenance` is one record per *written* field: `(field, value, source,
  confidence, fetched_at)`.
- Pure/deterministic given provider outputs — unit-testable with fake providers, zero
  network.

### 3. Provenance table + canonical column write-through — migration `0008`

New table **`lead_enrichments`** (append-only audit of who-said-what):

| col | type |
|---|---|
| id | uuid pk |
| lead_id | uuid fk → leads.id (ON DELETE CASCADE) |
| field | text |
| value | text |
| source | text |
| confidence | float |
| fetched_at | timestamptz (server default now) |

New **canonical columns** (the values the engine actually reads; provenance stays the
audit trail): `Lead.phone` (text, null); `Company.industry`, `Company.size`,
`Company.description` (text, null). No index beyond the `lead_id` FK — provenance is
read per-lead.

**Write-through rule (the anti-clobber invariant):** the chain writes a canonical column
**only if it is currently NULL/empty**. A title/name the operator supplied via CSV is
never overwritten by a provider. Every field the chain *considered* still lands in
`lead_enrichments` (so provenance shows "apollo said X but CSV already had Y"); only empty
canonical columns get filled. `company_*` fields resolve/attach the `Company` by domain
(reuse existing get-or-create if present; else add a tiny helper).

### 4. Config — provider keys + chain order (`config.py`)

```python
apollo_api_key: str = ""
hunter_api_key: str = ""
# comma-separated precedence order; empty = enrichment disabled (verify-only).
# a provider whose key is blank is silently skipped.
enrichment_providers: str = ""     # e.g. "apollo,hunter"
```

A `build_enrichment_chain(settings)` factory returns the ordered, key-present providers
(or `[]`). Empty chain ⇒ enrichment is a no-op and only verify runs — the honest default
for a fresh self-host with no keys. **These are new knobs, not changed defaults**, so no
⛔ gate on the config itself (the ⛔ Gate M2 covers the scoring-weight change in M2.3, not
this).

### 5. Wire into the pipeline — extend `enrich_lead` (`workers/tasks.py`)

`enrich_lead` becomes **verify → enrich**, in that order:

1. `verify_email` exactly as today → set `email_verified` / `status` (unchanged).
2. **Only if verified** (don't spend API budget on dead addresses): build the chain from
   settings; if non-empty, run `chain_enrich`, write `lead_enrichments` rows, fill empty
   canonical columns, and set `lead.source` to the winning provider when the lead had no
   real source. All of step 2 is wrapped so any failure leaves the verified lead intact.

Import trigger at `leads.py:26-29` is unchanged (already enqueues `enrich_lead`).

### 6. Minimal read surface — `GET /leads/{id}/enrichments` (read scope)

Returns the provenance rows (`field, value, source, confidence, fetched_at`) as a typed
list — this is the "results stored with provenance" the roadmap asks for, made inspectable.
Light UI: the existing leads page (M1.3) gains a small **source badge** per lead and the
row's detail popover lists provenance. If the UI portion balloons, it ships as provenance
JSON behind the endpoint and the badge only — surfacing depth is the flex, the endpoint +
storage are the commitment.

## Tests (0 skipped)

- **Contract** `tests/unit/test_enrichment_providers.py`: recorded Apollo + Hunter JSON
  fixtures → patched `_fetch` → assert correct `EnrichmentResult.fields` mapping, empty
  values dropped, `source`/`confidence` set. (Predict-then-run per `TESTING.md` §3.)
- **Chain** `tests/unit/test_enrichment_chain.py`: two fake providers, precedence order
  respected; per-field first-writer-wins; provenance record per written field; empty chain
  ⇒ `({}, [])`.
- **Anti-clobber** (adversarial, `tests/adversarial/test_enrichment_attacks.py`):
  - provider raises / times out / returns HTTP 500 / malformed JSON ⇒ chain continues,
    verify result untouched, no partial/garbage canonical write, no crash;
  - a provider value **must not overwrite** a non-null CSV field, but **must** still be
    recorded in `lead_enrichments`;
  - all-providers-fail ⇒ lead still ends `verified`, zero enrichment rows.
- **E2E** `tests/e2e/test_enrich_pipeline.py`: import → `enrich_lead` (patched providers)
  → lead verified + canonical columns filled + provenance rows present; `GET
  /leads/{id}/enrichments` returns them under `read` scope, 401 without a key, 404 unknown
  id. `enrichment_providers=""` ⇒ verify-only, zero enrichment rows.
- **Migration** `0008` upgrades from `0007` on a fresh Postgres and downgrades one step
  (CI pattern from M0.2).

## Out of scope (named so it isn't mistaken for missing)

- **Lead *sourcing*** (searching for new leads) — that's **M2.2** (`LeadSourceProvider`,
  `POST /leads/source`, "Find leads" page). M2.1 enriches leads that already exist.
- **Intent signals / scoring-weight change** — **M2.3** (the `0.6·cosine + …` reweight is
  the ⛔ Gate M2 item; M2.1 touches no scoring weights).
- **Per-org / DB-backed encrypted provider credentials** — keys are process-level env
  config now; per-org keys arrive with multi-tenancy in **M5.1**.
- **New enrichment providers beyond Apollo/Hunter** — the protocol makes them cheap later;
  M2.1 ships exactly the two that already have code, plus `null`.
