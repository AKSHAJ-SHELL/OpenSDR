# Plan — Epic M0.1: Authentication & authorization (A1)

**Branch:** `m0.1-auth` · **Status:** open questions resolved by human 2026-07-20; awaiting final go-ahead · **Roadmap:** M0.1 · **Finding:** A1 (`APPLICATION_OVERVIEW.md` §11)

## Goal

Every API endpoint except `/health` and `/u/{token}` requires a scoped, hashed-at-rest
API key via `Authorization: Bearer`. The dashboard gets a session login (single admin)
and all its API calls carry auth without ever exposing a key to the browser.

## Current state (verified in code)

- `craftsman/api/app.py` — FastAPI app, 6 routers, no middleware except CORS, `/health` inline.
- 19 routes total (leads, campaigns, inbox, mailboxes, analytics, unsubscribe). The only
  dependency anywhere is `get_db`. No auth of any kind.
- `web/src/lib/api.ts` — plain `fetch` against `API_URL` (server) / `NEXT_PUBLIC_API_URL`
  (browser). No headers beyond Accept/Content-Type. Next.js 16.2.10.
- `craftsman/core/crypto.py` — Fernet keyed by `CRAFTSMAN_SECRET_KEY` (already required
  for mailbox credentials).
- No Alembic yet (lands in M0.2) — `init_db()` uses `create_all`, so the new table below
  rides that for now and gets captured in M0.2's baseline migration.

## Design

### 1. API keys (server)

**New table `api_keys`** (in `craftsman/core/models.py`):

| column | type | notes |
|---|---|---|
| `id` | UUID pk | |
| `name` | str | human label ("dashboard", "ci") |
| `key_prefix` | str(12) | first chars of the token, for identification in UI/logs |
| `key_hash` | str(64), unique, indexed | SHA-256 hex of the full token |
| `scopes` | JSON list | subset of `["read", "operate", "admin"]` |
| `created_at`, `last_used_at`, `revoked_at` | timestamps | revoked ⇒ 401 |

**Token format:** `csk_` + 32 bytes `secrets.token_urlsafe`. Shown exactly once at
creation; only the SHA-256 digest is stored. Plain SHA-256 (not bcrypt/argon2) is
correct here: the token is high-entropy random, so brute-forcing the digest is
infeasible and lookup stays O(1) by hash — this is the standard API-key pattern
(GitHub/Stripe do the same).

**Scopes** (hierarchical: `admin` ⊃ `operate` ⊃ `read` — see Open Questions #1):

| scope | routes |
|---|---|
| `read` | all GETs: `/leads`, `/campaigns`, `/campaigns/{id}`, `/campaigns/{id}/bandit`, `/inbox`, `/inbox/review`, `/mailboxes`, `/analytics/overview`; also `/docs` + `/openapi.json` (see below) |
| `operate` | `POST /leads/import`, `POST /campaigns`, `POST /campaigns/{id}/variants`, `/activate`, `/pause`, `POST /inbox/{id}/reclassify` |
| `admin` | `POST/PATCH /mailboxes`, `DELETE /leads/{id}/erase`, all `/keys` endpoints |
| *(none)* | `GET/POST /u/{token}` (RFC 8058 requires unauthenticated POST), `GET /health` |

**Enforcement mechanism:** a `require_scope(scope)` dependency factory in a new
`craftsman/api/auth.py`, built on FastAPI's `HTTPBearer` (so `/docs` documents the
scheme). It: extracts the bearer token → SHA-256 → DB lookup → reject if missing or
`revoked_at` set → check scope → stamp `last_used_at` (best-effort, no extra round trip
blocking the request). Wired **per-router** via `APIRouter(dependencies=[...])` for the
default scope, with per-route overrides where a router mixes scopes (leads: read GET /
operate import / admin erase; campaigns: read GETs / operate POSTs; inbox: read GETs /
operate reclassify).

**Fail-closed guard:** because per-router wiring can be forgotten on a future router, a
unit test walks `app.routes` and asserts every route is either in the explicit
unauthenticated allowlist (`/health`, `/u/{token}`, docs routes) or carries an auth
dependency. A new unauthenticated route fails CI by default.

**`/docs` and `/openapi.json` are auth-gated** (human decision 2026-07-20: not publicly
exposed). FastAPI's built-in doc routes can't take dependencies, so the app is created
with `docs_url=None, redoc_url=None, openapi_url=None` and two custom routes serve
`get_swagger_ui_html` and `app.openapi()` behind `require_scope("read")`. Practical
consequence, documented in the README: a plain browser visit to `/docs` gets 401 (a
browser can't attach a Bearer header on page load), so interactive exploration means
fetching the spec with a key (`curl -H "Authorization: Bearer csk_…" :8000/openapi.json`)
into any OpenAPI viewer. The gate's real job is closing the surface-enumeration leak on
`/openapi.json`.

**Error semantics:** missing/malformed/unknown/revoked key → `401` with
`WWW-Authenticate: Bearer`; valid key, insufficient scope → `403` naming the required
scope. Key values never appear in logs or error bodies (only `key_prefix`).

**Key management endpoints** (new router `craftsman/api/routers/keys.py`, admin scope):

- `POST /keys` `{name, scopes}` → `{id, name, scopes, token}` — token returned once.
- `GET /keys` → list (id, name, prefix, scopes, created/last-used/revoked). Never the hash.
- `DELETE /keys/{id}` → sets `revoked_at` (soft revoke; audit trail survives).

**Bootstrap** (first key, when no admin key exists yet): CLI command
`python -m craftsman.create_key --name bootstrap --scopes admin` that talks straight to
the DB and prints the token. Referenced from the quickstart. No auto-generated key on
startup, no "auth disabled" env flag — the API is never fail-open. `scripts/seed_demo.py`
and `scripts/e2e_demo.py` create their own key via the same code path and use it.

### 2. Dashboard session login (web)

Single admin user; real user model is M5.1's job.

- **Credential:** `DASHBOARD_PASSWORD_HASH` env var on the web container — a bcrypt
  hash, verified with `bcrypt.compare` (constant-time by construction). A helper
  generates it: `node web/scripts/hash-password.mjs <password>` (documented in the
  quickstart and `.env.example`). Startup fails loudly if the var is unset or not a
  valid bcrypt hash — never fail-open.
- **Session:** `POST /api/login` route handler checks the password and sets an
  HMAC-signed, httpOnly, SameSite=Lax cookie (`craftsman_session`, 7-day expiry), signed
  with `DASHBOARD_SESSION_SECRET`. `POST /api/logout` clears it. Next.js `middleware.ts`
  redirects every page except `/login` to `/login` when the cookie is missing/invalid.
- **API key handling — the browser never sees a key.** Today `api.ts` fetches from both
  server components (`API_URL`) and the browser (`NEXT_PUBLIC_API_URL`). Change:
  - Server-side calls attach `Authorization: Bearer ${CRAFTSMAN_API_KEY}` (web-container
    env; a key with `read` + `operate` scopes — the dashboard has no admin surface yet).
  - Browser-originated calls (the mutating ones: activate, pause, reclassify) go through
    a Next route handler `/api/proxy/[...path]` that verifies the session cookie, then
    forwards to the API with the server-held key. `NEXT_PUBLIC_API_URL` direct-from-browser
    usage is removed.
- Login page: minimal, matches existing dashboard styling.

### 3. Config & docs

- `Settings` gains nothing server-side (keys live in the DB); web env gains
  `DASHBOARD_PASSWORD_HASH`, `DASHBOARD_SESSION_SECRET`, `CRAFTSMAN_API_KEY`.
- `.env.example` + `docker-compose.yml`: new vars documented; compose keeps binding to
  localhost.
- README: quickstart adds the bootstrap-key step and a **loud warning** — exposing port
  8000/3000 beyond localhost without keys+login publishes your lead database and a mail
  cannon. API docs section documents scopes per endpoint.
- Knobs table (`APPLICATION_OVERVIEW.md` §10): add the three web env vars + token format.

## Tests

`tests/unit/test_auth.py`, `tests/e2e/test_auth_integration.py`, and
`tests/adversarial/test_auth.py` (predict-then-run per `TESTING.md` §3; auth is in the
adversarial-debt scope per roadmap §9.3):

1. **Every endpoint 401s without a key** — parametrized over `app.routes` minus
   allowlist; includes the custom `/docs` and `/openapi.json` routes.
2. **Fail-closed route walk** — the allowlist test described above.
3. **Scope matrix** — read key on operate/admin routes → 403; operate on admin → 403;
   admin passes everywhere; correct scope passes.
4. **Unsubscribe stays anonymous** — `GET` and `POST /u/{token}` with no header succeed;
   `/health` likewise.
5. **Key lifecycle** — create returns token once; token authenticates; revoke → 401;
   `last_used_at` advances; `GET /keys` never leaks hash or token.
6. **Adversarial:** empty bearer, `Bearer` with no value, wrong prefix, valid-format
   unknown token, revoked-then-reused token, token in query string (must not work),
   scheme confusion (`Basic`, lowercase `bearer`), oversized token, unicode token.
7. **Web:** login sets cookie only on a password matching `DASHBOARD_PASSWORD_HASH`;
   wrong password → 401; startup refuses to serve with a missing/malformed hash; proxy
   rejects requests without session; middleware redirects unauthenticated page loads.

Suite must end green, 0 skipped, Postgres up.

## Out of scope (deliberately)

- Multi-user, orgs, RBAC roles, SSO → M5.1. Rate limiting on login → M5. Alembic → M0.2
  (the `api_keys` table will be in its baseline). Dashboard admin surfaces (key
  management UI, erase button) → M1.3.

## Open questions — RESOLVED (human, 2026-07-20)

1. **Scope hierarchy:** ✅ approved — `admin ⊃ operate ⊃ read`.
2. **Campaign/variant creation + CSV import:** ✅ `operate` — the human's framing:
   whatever role a logged-in dashboard user maps to should be able to do these. The
   dashboard's key is `read`+`operate`, so these are `operate`.
3. **Dashboard password:** ✅ hashed — `DASHBOARD_PASSWORD_HASH` (bcrypt) in web env,
   with a bundled hash-generator helper.
4. **`/docs`:** ✅ not publicly exposed. (Requested as ".gitignored" — `/docs` is
   FastAPI's runtime Swagger endpoint, not a repo file, so the equivalent is gating it:
   `/docs` + `/openapi.json` require `read` scope. See the design note above.)
