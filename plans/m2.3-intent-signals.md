## Goal

Prioritize leads by **intent** — funding, hiring, tech-stack moves — not just static fit.
A signal engine collects observations per company (each collector optional and
independently disableable), a **decaying** signal component feeds the ICP score, and
`signal_rules` can boost, notify, or **auto-enroll** on a match. Two things here change
*who gets emailed*, so this epic ends at **⛔ Gate M2**: (1) the scoring reweight, and
(2) the signal-triggered enrollment policy. I will not touch the scoring formula or ship
auto-enroll until both are signed off (questions at the bottom).

## Design

### 1. Tables + provenance column — migration `0009`

- **`signals`** — `id`, `company_id` FK (no cascade, M0.4 doctrine), `type`
  (`funding | leadership_hire | job_posting | tech_stack_change`), `payload` JSONB,
  `observed_at` timestamptz, `source` text. Index `(company_id, type, observed_at)`.
- **`signal_rules`** — `id`, `campaign_id` FK, `signal_type`, `action`
  (`boost_score | enroll | notify`), `active` bool. A campaign's operator declares which
  signals matter and what happens.
- **`collector_state`** — `id`, `company_id` FK, `collector` text, `fingerprint` text,
  `updated_at`. Diffing needs the prior fingerprint; storing it here (not in `signals`)
  keeps "a change happened" separate from "here's the raw page hash."
- **`leads.icp_signal`** — Float, nullable. The third score-provenance component (mirrors
  `icp_cosine`/`icp_rule`), so the popover explains the signal contribution truthfully.

Recent, high-weight signals push toward 1.0; old ones decay geometrically. Pure and fully
unit-tested (age 0 → full weight; age = half_life → half; clamp at 1.0; empty → 0.0).
`signal_half_life_days` is a config knob (default **30**).

### 3. Scoring integration — the ⛔ reweight (`scoring/icp.py`)

Weights move to config (`icp_cosine_weight`, `icp_rule_weight`, `icp_signal_weight`) so
they're inspectable knobs. `score_breakdown(..., signal_boost=0.0)` gains a `signal`
component; `ScoreBreakdown` gains `signal`. `activate` computes each lead's boost from its
company's signals, passes it in, and stores `lead.icp_signal`.

**The formula default is a ⛔ decision (Question 1).** With `signal_boost=0`, the
roadmap-literal `0.6·cos + 0.25·rule` scores *lower* than today's `0.7·cos + 0.3·rule` for
the same lead — so even operators with **no signals configured** would see some
currently-emailed leads drop below threshold. Three options, in §Gate below.

### 4. Collectors — `scoring/collectors.py` (new) + config gating

`SignalCollector` protocol: `name`; `collect(db) -> list[CollectedSignal]`. Each iterates
companies with a domain, is failure-isolated per company (one bad fetch never sinks the
sweep), and is enabled only if listed in `signal_collectors` config. Implementations cover
all three roadmap categories with two mechanisms:

- **`HomepageDiffCollector`** → `tech_stack_change`. `fetch_company_text(domain)` →
  fingerprint (hash of cleaned text) → compare to `collector_state` → emit on change.
  First sight seeds a baseline (no signal). Honest labeling: this is a coarse
  "homepage changed" signal, not semantic tech extraction.
- **`CareersDiffCollector`** → `job_posting`. Same mechanism against `/careers`, `/jobs`
  (SSRF-guarded). A change = hiring activity. (Distinguishing a *leadership* hire needs
  parsing; noted as future — the `leadership_hire` type exists for a keyed job-board
  source later.)
- **`RssFundingCollector`** → `funding`. GET `signal_funding_rss_url` (SSRF-guarded),
  parse entries, match a company by name/domain, emit per new entry (dedupe via
  `collector_state` on the entry id). This is the keyless "RSS/news watch" the roadmap
  offers as the alternative to a BYO Crunchbase key. A `CrunchbaseCollector` keyed slot is
  a documented future provider (same extensibility as M2.1/M2.2 — mechanism now, more
  sources later); not claimed as shipped.

New beat entry `collect-signals` (default daily) runs enabled collectors, persists
`signals`, then evaluates `signal_rules` (§5). Empty `signal_collectors` ⇒ the sweep is a
no-op — the honest default.

### 5. Rule evaluation + signal-triggered enrollment — the ⛔ policy

After collection, for each new signal, matching `active` `signal_rules` fire:
- **`boost_score`** — no-op at fire time; the signal already feeds scoring via
  `signal_boost` on the next `activate`/score. (Recorded so the operator sees intent.)
- **`notify`** — Slack ping (reuse `slack_webhook_url`), never mutating state.
- **`enroll`** — for each **verified, above-threshold** lead at the signal's company **not
  already enrolled** in the rule's campaign, create `Enrollment(state="queued",
  current_step=0, next_action_at=now)` — identical to `activate`. The state machine then
  runs research → fill → validate → send exactly as normal. **Never** skips a step; an
  `enroll` on an unverified or below-threshold lead is a no-op (logged).

**Whether `enroll` ships at all, and its default, is a ⛔ decision (Question 2).**

### 6. API + web (minimal, read-first)

- `GET /campaigns/{id}/signal-rules`, `POST` (operate), `DELETE` (operate) — manage rules.
- `GET /companies/{id}/signals` or `GET /leads/{id}/signals` (read) — surface the
  observations behind a lead's boost (feeds the score popover's new third row).
- `ScoreCell` gains the **signal** row; weights come from the API (a small
  `GET /config/scoring-weights` or fields on the score response) so the explanation stays
  truthful when the knobs change — no more hardcoded 0.7/0.3 in the client.
- A light per-campaign signal-rules editor. (No new top-level page; rules live on the
  campaign detail. Signal *observation* is background — no dashboard page needed in M2.3.)

**Q1 — scoring formula when a lead has no signals** (this changes who gets emailed):
- **A. Flat / roadmap-literal:** always `0.6·cos + 0.25·rule + 0.15·boost`. No-signal

- **B. Renormalized (recommended):** no-signal leads keep today's `0.7·cos + 0.3·rule`;
  only leads *with* signals use the 3-way split. Zero change for operators without
  signals — honors "no silent guarantee changes."
- **C. Additive bonus:** `0.7·cos + 0.3·rule + 0.15·boost`, clamped to 1.0. Signals only
  ever *raise* a score.

**Q2 — signal-triggered auto-enrollment:**
- **A. Ship `enroll`, OFF by default (recommended):** no rule exists until an operator
  creates one; guardrails = verified + above-threshold + not-already-enrolled + lands in

- **B. Ship boost/notify only:** defer `enroll` entirely to a later, explicitly-opted-in
