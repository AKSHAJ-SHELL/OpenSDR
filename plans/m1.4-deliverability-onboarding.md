# Plan — Epic M1.4: Deliverability onboarding (C3)

**Branch:** `m1.1-campaign-builder` (M1 line, stacked on `m0.1-auth`) · **Status:** implemented · **Roadmap:** M1.4

## Goal

Make a new operator confident their mail will actually land before they send. Three
things have no surface today: (1) whether a sending domain's **SPF / DKIM / DMARC** are
configured — verified by live DNS lookup, with copy-paste values to fix what's missing;
(2) the **warmup ramp** — where each mailbox is on it and what the day-by-day schedule
is; (3) the single most important piece of unwritten advice — **do not send from your
primary domain.** This is the last M1 epic before the Gate M1 golden-path review.

## Current state (verified in code)

- **`dnspython>=2.6` is already a dependency** (`pyproject.toml:20`) and
  `craftsman/ingest/verify.py:9-10,22` already resolves MX records. The test pattern for
  DNS is monkeypatching the module's resolver function (see `_resolve_ips` in

- **Warmup already exists and auto-ramps.** `sender/warmup.py` has

  (stage ≥4 → full `daily_limit`). `reset_daily_counters` (`workers/tasks.py:439-443`)
  advances `warmup_stage` by one **per calendar day**. So the ramp schedule is *derivable*

- **`Mailbox`** (`core/models.py:187`) has `email`, `daily_limit` (40), `sent_today`,

- **No mailbox UI.** The dashboard only renders a health badge per mailbox in the

  manage or inspect one.
- **No deliverability guidance anywhere in the product.** README has a strong narrative
  in "Why this exists" / "What it will never do" but no SPF/DKIM/DMARC/primary-domain
  section, and it sits *below* the quickstart.

## Design

### 1. DNS auth checking — `craftsman/deliverability/dns_auth.py` (new)

One thin, monkeypatchable seam plus pure parsers (unit-tested with no network):

```
resolve_txt(name, timeout=5.0) -> list[str]     # the ONLY network call; tests patch this
check_spf(domain)   -> SpfResult(status, record)
check_dmarc(domain) -> DmarcResult(status, policy, record)   # _dmarc.<domain>
check_dkim(domain, selector=None) -> DkimResult(status, selector, record)
```

Honesty rules baked into the design (this is the repo's whole ethos):
- **SPF** and **DMARC** we can hand the operator a concrete copy-paste value. DMARC is
  fully generatable: `v=DMARC1; p=none; rua=mailto:dmarc@<domain>` as a safe starter.
  SPF depends on the provider's `include:`, so the recommended value is a template with a
  clearly-marked `include:_spf.YOUR-PROVIDER` placeholder — we never fabricate a provider.
- **DKIM** keys are minted by the *sending provider*, not by us — we cannot generate the
  value. So DKIM is **verify-only**: check the stored selector if set, else probe a short
  list of common selectors (`google`, `default`, `selector1`, `selector2`, `k1`, `dkim`,
  `s1`, `mail`) and report which one (if any) resolves. The UI guidance says "get this
  from your provider," never invents a key.
- `status` is one of `pass` / `missing` / `error` (error = DNS timeout/SERVFAIL, so a
  flaky resolver reads as "couldn't check", never a false "missing").

### 2. Warmup schedule — extend `sender/warmup.py`

Add `warmup_schedule(daily_limit) -> list[{day, stage, cap}]` derived from `WARMUP_CAPS`
(pure function, unit-tested). No behavior change to sending.

### 3. Primary-domain heuristic — in `dns_auth.py`

`looks_like_primary_domain(domain) -> bool`: soft signal — true when the domain has ≤2
labels (`acme.com`) rather than a dedicated subdomain (`outbound.acme.com`). The guidance
banner is **always** shown on the page; the heuristic only escalates it to a per-mailbox
warning. No public-suffix dependency added (kept deliberately soft and honest about being
a heuristic).

### 4. Mailbox DKIM selector — migration `0007`

Add nullable `dkim_selector` to `mailboxes` (+ `MailboxCreate`/`MailboxUpdate`/`MailboxOut`).
Optional; when set it's the authoritative selector for the DKIM check, otherwise we probe.

### 5. API — `GET /mailboxes/{id}/deliverability` (read scope)

Returns a typed `DeliverabilityReport`:
```
domain, primary_domain_warning: bool,
spf:   {status, record, recommended},
dmarc: {status, policy, record, recommended},
dkim:  {status, selector, record},
warmup:{stage, effective_cap, daily_limit, sent_today, advances_per_day: 1,
        schedule: [{day, stage, cap}, ...]}
```
Live DNS lookups run server-side with per-record timeouts. 404 for a missing mailbox.
Scope `read` (records aren't secret; consistent with `GET /mailboxes`).

### 6. Web — `/deliverability` page (new) + sidebar entry

Server component, one card per mailbox (fetches the report per box):
- **SPF / DKIM / DMARC** rows: status pill (pass/missing/couldn't-check) + the found
  record (monospace) + a copy-paste block with a copy button for the recommended value
  (SPF/DMARC) or provider guidance (DKIM).
- **Warmup ramp**: current stage highlighted, today's effective cap vs `sent_today`, and
  the day-by-day schedule (10 → 20 → 30 → 40 → full).
- **"Don't send from your primary domain"** guidance banner, front and center, escalated
  per-mailbox when the heuristic fires.
- Empty state when no mailboxes: point at `POST /mailboxes` (admin).
- Sidebar gains a **Deliverability** entry; the Overview Mailboxes tile links to it.

Copy button is a tiny client component; the page itself is a server component (matches the
leads/review pattern). No new browser POST — the page is read-only, so the `:3000` CORS
constraint doesn't bite here.

## Tests (0 skipped)

- **Unit** `tests/unit/test_dns_auth.py`: SPF present/absent/multiple-TXT; DMARC policy
  extraction (`p=none|quarantine|reject`) + `_dmarc` name; DKIM stored-selector hit,
  common-selector probe hit, all-miss; `error` on resolver raising; parsers never touch
  the network (patch `resolve_txt`).
- **Unit** `tests/unit/test_warmup_schedule.py`: schedule shape for default and custom
  `daily_limit`; `looks_like_primary_domain` boundary cases.
- **E2E** `tests/e2e/test_deliverability.py`: `GET /mailboxes/{id}/deliverability` with a
  patched resolver returns correct statuses + warmup block; `read`-scope gated; 404 for
  unknown id; `dkim_selector` round-trips through create/update.
- **Adversarial** `tests/adversarial/test_dns_auth_attacks.py` (network-boundary
  robustness per `TESTING.md` §3 predict-then-run): resolver timeout / NXDOMAIN /
  malformed TXT / a TXT that merely *contains* `v=spf1` mid-string all resolve to a safe
  `missing`/`error`, never a crash or a false `pass`.

  these are **M5.3 Deliverability suite** (`ROADMAP.md:342`), which explicitly consumes
  "DNS auth status (from M1.4)". This epic is the onboarding checklist, not the ongoing
  monitor.

- Changing any warmup cap or the one-stage-per-day cadence (⛔ knob-default change).
