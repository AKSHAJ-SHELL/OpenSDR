# Plan — Epic M0.6b: Observability & operational recovery (D2)

**Branch:** `m0.1-auth` (M0 line) · **Status:** awaiting approval · **Roadmap:** M0.6 (split; this is the observability half) · **Finding:** D2

## Goal

Make a running deployment inspectable and recoverable: structured logs with correlation
IDs, a Prometheus `/metrics` endpoint, a dead-letter record for exhausted Celery retries,
and a re-drive path so a stuck `error` enrollment (or a genuinely-unsent claim from 0.6a)
isn't stuck forever.

## Current state (verified in code)

- **Logging:** none configured — every module does `logging.getLogger(__name__)` and logs
  go wherever the default handler sends them (plain text, no structure, no IDs).
- **Metrics:** none. `/health` exists; no `/metrics`.
- **Dead-letter:** none. `generate_and_send` has `max_retries=3`; on the 4th failure the
  task just dies — no record. Redis broker has no native DLQ.
- **`error` state is terminal** (`machine.py:27`). Reached by `RESEARCH_FAILED`,
  `SEND_FAILED`, and the copywriter double-rejection (`tasks.py:130` sets
  `state="error"` + a `ReviewQueueItem(kind="copywriter")`). Nothing moves it back.
- Review endpoint returns items but **not `enrollment_id`** — the UI can't act on them.
- Celery queues: `enrich, research, send, inbox, settle`.

## Design — four phases, each independently testable

### Phase 1 — Structured JSON logging + correlation IDs

- New deps: `python-json-logger`. `craftsman/core/logging.py`:
  - `configure_logging()` installs a JSON formatter on the root logger (fields: ts, level,
    logger, message + any bound IDs); level from `LOG_LEVEL` (default INFO). Called from the
    API lifespan and a Celery `worker_process_init` signal.
  - Correlation IDs via `contextvars`: `bind_log_context(lead_id=…, enrollment_id=…,
    message_id=…)` sets a contextvar; a `logging.Filter` merges it into every record. The
    task entrypoints (`research_enrollment`, `generate_and_send`, `handle_inbound`) bind the
    ids they know, so every downstream log line is traceable to a lead/enrollment/message.

### Phase 2 — Prometheus `/metrics`

- New dep: `prometheus-client`. **Pull-based, computed at scrape time** — the honest choice
  for separate api/worker processes (in-process counters in a worker are invisible to the
  API that serves `/metrics`). A custom collector queries the shared stores on each scrape:
  - from Postgres: `craftsman_enrollments{state}`, `craftsman_leads{status}`,
    `craftsman_outbound_sent_today`, `craftsman_replies{classification}`,
    `craftsman_review_queue{kind}`, `craftsman_dead_letters`.
  - from Redis: `craftsman_queue_depth{queue}` (LLEN of each Celery queue),
    `craftsman_send_rejections_total{reason}` (small Redis INCR counters written by workers
    at each `SendBlocked` — the only event not otherwise persisted; cross-process via Redis).
- `GET /metrics` returns `generate_latest()`. **Auth: gated behind `read` scope** like
  `/docs` (Prometheus scrapes with a bearer token) — see open question #2.

### Phase 3 — Dead-letter for exhausted retries

- Migration `0003`: `dead_letters` table (id, task_name, args JSON, kwargs JSON,
  exception, traceback, enrollment_id NULL, created_at).
- A Celery `task_failure` signal handler records a row when a task fails **terminally**
  (retries raise `Retry`, which is not a failure, so this fires only after retries are
  exhausted). Best-effort: never let dead-letter recording mask the original error.
- Surfaced via the `craftsman_dead_letters` metric and a read endpoint `GET /dead-letters`.

### Phase 4 — Re-drive (unstick `error` enrollments and unsent claims)

- **Service** `redrive_enrollment(db, enrollment, action)` in the sequencer, imperative
  (a human/admin recovery action, logged to `audit_log`):
  - `retry` → re-enter the pipeline: `ready` if a research brief exists, else `queued`;
    `next_action_at = now`.
  - `skip` → advance `current_step` and set `ready`; past the last step → `finished_no_reply`.
  - `kill` → leave terminal (stays `error`); just resolve the review item (give up).
- **Endpoint** `POST /inbox/review/{item_id}/action` `{action}` (operate scope): applies the
  action to the item's enrollment and marks the item resolved. The `/review` response gains
  `enrollment_id` so the UI can show/act.
- **Unsent-claim sweep** (the 0.6a residual): a beat task `redrive_unsent` finds outbound
  `messages` with `sent_at IS NULL` older than N minutes (a hard-crash claim), deletes the
  stuck claim, `release_campaign_slot`, and sets the enrollment back to `ready` so the next
  tick re-sends. Interval + age threshold are config knobs.

## Tests

- **Logging (unit):** `configure_logging` emits valid JSON; the context filter injects bound
  ids; `bind_log_context` is isolated per contextvar.
- **Metrics (integration):** with seeded DB state, `/metrics` (with a `read` key) returns the
  expected gauges/values; 401 without a key; a Redis rejection counter shows up.
- **Dead-letter (integration):** simulate a terminal task failure → a `dead_letters` row is
  written with the task name + exception; the metric reflects it.
- **Re-drive (integration):** an `error` enrollment + copywriter review item → `retry` returns
  it to `ready`/`queued` and resolves the item; `skip` advances the step; `kill` resolves
  without reactivating. The unsent-claim sweep deletes a stale `sent_at IS NULL` claim,
  frees the campaign slot, and re-readies the enrollment; a fresh (recent) claim is left alone.

Existing tests pass unmodified. Suite green, 0 skipped, Postgres up. Migration `0003`
upgrade/downgrade + `alembic check` clean.

## Out of scope

Tracing/OpenTelemetry, Grafana dashboards, alerting rules, multi-tenant metric labels
(D3/M5). Log shipping/retention is deployment config, not code.

## Open questions for approval

1. **New deps** `prometheus-client` + `python-json-logger` (pyproject edit + `pip install`).
   Proposed: yes.
2. **`/metrics` gated behind `read` scope** (Prometheus uses a bearer token), consistent with
   `/docs`, vs. left open (easier scraping, but leaks send/pipeline volumes on an exposed
   port). Proposed: gate behind `read`.
3. **Dead-letter as a DB table + `task_failure` signal** (Redis has no native DLQ). Proposed:
   yes. Alternative (a Redis dead-letter list) loses queryability and the enrollment link.
4. **Re-drive `kill` leaves the enrollment in `error`** (resolved, no new state) vs. adding a
   dedicated `killed` terminal state. Proposed: reuse `error` + resolved to avoid a machine
   change; a `killed` state is a bigger change for little gain.
5. **Landing:** four phases as **four commits** on this branch (my recommendation — each is
   independently reviewable and testable), or one combined 0.6b commit. Proposed: four commits.

## Implementation order (one commit per phase if #5 = split)

1. Logging: `core/logging.py` + context filter + task binding + startup wiring + unit tests.
2. Metrics: `core/metrics.py` collector + `/metrics` endpoint (read-gated) + rejection
   counters at `SendBlocked` sites + integration tests.
3. Dead-letter: migration `0003` + `task_failure` handler + `GET /dead-letters` + tests.
4. Re-drive: `redrive_enrollment` service + review action endpoint (+`enrollment_id` in
   `/review`) + `redrive_unsent` beat task + config knobs + tests. Docs: knobs table, D2 →
   resolved, README ops note, `findings/08`.
