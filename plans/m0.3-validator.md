# Plan — Epic M0.3: Validator numeric grounding (B1) 🎯

**Branch:** `m0.1-auth` (M0 line) · **Status:** approved by human 2026-07-21 (Q1 yes; Q2 symbol-insensitive per roadmap — "£4M grounds against $4M"; Q3 delegated, suffix reading chosen) · **Roadmap:** M0.3 · **Finding:** B1

## Goal

Split the grounding gate into two paths: entities keep `partial_ratio ≥ 90`; **numbers,
currency, percentages, and dates get exact match after normalization**. `$4M` must ground
against `$4,000,000` and must NOT ground against `$40M`. `1,000` must ground against
`1000`. The full adversarial table from `TESTING.md` §3.1 becomes a permanent regression
suite.

## The bug, precisely (verified in `craftsman/copywriter/validator.py`)

1. **Numbers ride the fuzzy path.** `validate_fill` sends `proper + numbers` through the
   same `_grounded()` (line 119), which passes anything with
   `fuzz.partial_ratio ≥ 90` (line 93). `partial_ratio("10,000", "…1,000…")` ≥ 90 because
   `1,000` aligns as a 6-of-7-char window of `10,000` — a 10× hallucination passes.
2. **Extraction is blind to units.** `_NUMBER_RE = \b\d[\d,]*(?:\.\d+)?%?` (line 40)
   captures neither currency symbols nor magnitude suffixes: `$40M` extracts as just
   `40`. The gate literally cannot see the difference between $40M and 40 people.
3. **No normalization.** `1,000` vs `1000` only passes today if fuzzy happens to clear 90
   — separator-insensitive equality is luck, not policy.

## Design

### 1. Numeric extraction (`_NUMERIC_RE` replaces `_NUMBER_RE`)

Capture the full numeric token: optional currency symbol (`$ € £`), digits with
separators/decimals, optional magnitude suffix (`k K m M b B bn` and the words
`thousand million billion`), optional `%`. Examples of one token each:
`$4M` · `4,000,000` · `4.2M` · `12%` · `1000` · `€3.5bn` · `2024`.

### 2. Normalization (`normalize_numeric(token) -> (value, kind)`)

- Strip separators and whitespace; parse with `Decimal` (no float drift: `4.2M` →
  `4200000`, exactly).
- Expand magnitude suffixes: `k`→×10³, `m`→×10⁶, `b`/`bn`→×10⁹ (word forms too).
- `kind` ∈ `plain` | `percent` | `currency` — so `12%` and `$12` and `12` are
  distinguishable.

### 3. Matching rules (exact, not fuzzy)

Corpus numeric tokens are extracted + normalized once per validation. A fill token is
grounded iff a corpus token has the **same normalized value** and a compatible kind:

| Fill token | Grounds against | Rationale |
|---|---|---|
| `$4M` | `$4,000,000`, `$4M`, `4M` | roadmap: `$4M ≡ $4,000,000`; symbol stripped for matching |
| `$4M` | ~~`$40M`~~, ~~`$4.2M`~~ | different value → reject (silent rounding also rejects) |
| `1,000` | `1000`, `1,000` | separator-insensitive equality |
| `12%` | `12%` only — **not** bare `12` | a percent claim needs a percent source |
| `12` (bare) | `12`, `12%`, `$12` | the digits are genuinely present in the source |

Numbers are **removed from the fuzzy path entirely** — `validate_fill` grounds `proper`
via `_grounded()` (unchanged, threshold stays 90) and `numbers` via the new exact path.
Error messages name both the token and its normalized value so review-queue items are
self-explanatory.

### 4. Dates — deliberately no date parser

`TESTING.md` §3.1's date rows resolve without NLP:
- `March 2024` → `March` is already skipped (`_COMMON_CAPS`), `2024` is a numeric token
  → fill `2024` grounds exactly against the brief's `2024`. ✓
- `Q3 2025` vs fill `third quarter` → "third quarter" contains no digits and no
  capitalized tokens → nothing to ground → no false rejection. ✓
- `Q3` itself matches `_PROPER_RE` (capital+digit) and stays on the entity path.

If a real date-equivalence need appears later ("March 2024" ≡ "2024-03"), that's a new
epic — building a date grammar here would balloon scope.

### 5. What does NOT change

- `FUZZY_THRESHOLD = 90` for entities (a knob; changing it needs separate sign-off).
- Banned phrases, length caps, reading grade — untouched.
- No existing test is modified (working agreement §0).

## Tests

**New unit tests** (`tests/unit/test_validator_numeric.py`): the normalization table —
magnitude expansion, Decimal exactness (`4.2M ≠ 4M`), separator stripping, percent/
currency kinds, the mandated pairs (`$4M`→`$40M` rejects, `1,000`→`1000` passes).

**Adversarial regression suite** (`tests/adversarial/test_validator_attacks.py`), the
**full §3.1 table** with predict-then-run comments, per roadmap:
- Magnitude rows (`$4M/$40M`, `1,000/10,000`, `$4.2M/$4M` rounding) — must now reject.
- Normalization rows (`1,000/1000`, `Q3 2025/third quarter`) — must pass (no false rejection).
- Entity rows (`Acme Corp/Acme Group`, `Series A/Series B`, `Anthropic/Anthropics`),
  casing rows (`iPhone/deepmind/eBay`, sentence-initial nouns), date row, unit-swap row
  (`12%/12x`), banned-phrase variants (case, punctuation, unicode lookalikes,
  "Hope this email finds you well!"), and boundary length/grade cases — **characterized**
  with predictions. Where behavior is wrong outside the numeric scope, that's a
  **finding to flag** (`findings/04-…`), not a fix in this epic.

Suite ends green, 0 skipped, Postgres up. The copywriter retry loop's existing tests
(`test_copywriter_fill.py`, `test_validator.py`) must pass unmodified — if one fails,
stop and report per `TESTING.md` §0.

## Open questions for approval

1. **Percent strictness (my table above):** fill `12%` requires a percent source (so
   `12%` vs brief `12x` → reject), but a bare fill `12` may ground against `12%`/`$12`.
   Alternative: fully strict kinds both directions (bare `12` would then reject against
   `12%` — more false rejections, e.g. "12 warehouses" when the brief says "12%
   growth"... which is arguably a *correct* rejection). I propose the asymmetric rule.
2. **Currency symbols:** roadmap says "strip currency symbols", which makes `€4M` ground
   against `$4M`. That's a unit swap a strict reading would catch. I propose following
   the roadmap (strip symbols, value-only match) and noting the limitation in the plan +
   docs; flipping to symbol-strict later is a one-line rule change.
3. **Lowercase `m` ambiguity:** `4m` parses as 4 million under the suffix rule ("40m
   dash", "4m cable" would too). In sales-copy context I propose accepting the suffix
   reading unconditionally — false *rejections* here are cheap (copy goes to review),
   false *passes* are what we're killing. Confirm.
