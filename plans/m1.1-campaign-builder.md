# Plan — Epic M1.1: Campaign builder UI (G11)

**Branch:** `m1.1-campaign-builder` (stacked on `m0.1-auth` until the M0 PR merges; rebase onto main after) · **Status:** implemented (open questions resolved: block-and-clone; keep `slot_schema` auto-derived; expand GET additively) · **Roadmap:** M1.1

## Goal

Campaigns become creatable and editable in the dashboard: campaign fields → steps →
variants per step, with a skeleton editor that catches slot mistakes at authoring time
(today they explode at send time) and a live preview of the rendered email. Pure
surfacing — no new engine capability, no change to how copy is generated or validated.

## Current state (verified in code)

- **Create exists, read-back doesn't.** `POST /campaigns` creates campaign + steps from a
  `wait_days` list and embeds the ICP (`campaigns.py:37`). But `GET /campaigns/{id}`
  returns only `CampaignOut` — no steps, no variants, no persona. `VariantOut` omits
  `skeleton`/`slot_schema`. A UI cannot render what it cannot read.
- **No edit endpoints.** No PATCH for campaign, steps, or variants. Not even via curl.
- **`slot_schema` is write-only dead weight.** Stored on `Variant` (`models.py:109`),
  required by `VariantCreate`, never read anywhere — `fill.py` validates against the
  fixed `SlotFill` schema (4 LLM slots) regardless.
- **Skeleton contract (from `fill.py`):** placeholders are `{{subject_hook}}`,
  `{{personalization_sentence}}`, `{{value_prop_bridge}}`, `{{cta_question}}` (LLM) plus
  `{{first_name}}`, `{{signature}}` (static). `render_skeleton` raises on any leftover
  placeholder → a typo'd slot name fails at **send** time, lands the enrollment in
  `error`. The builder must catch this at authoring time.
- **Bandit state lives on the variant** (`alpha`, `beta`; trials = α+β−2). Editing a
  skeleton after an arm has trials silently rewrites what its posterior measured.
- **Web:** campaigns page is a read-only list whose empty state tells users to curl.
  Session-gated proxy exists; browser never sees the API key. `api.ts` has only
  `get`/`post` helpers. **`web/AGENTS.md` warns this Next.js version post-dates training
  data — implementation session must read `node_modules/next/dist/docs/` before writing
  any web code, and must verify the proxy route forwards PATCH.**

## Design — four phases

### Phase 1 — API: read-back + guarded edits (`craftsman/api/routers/campaigns.py`)

- `GET /campaigns/{id}` expands **additively** to `CampaignDetailOut`: existing fields +
  `sender_persona` + `steps: [{id, step_order, wait_days, variants: [{id, name, skeleton,
  slot_schema, alpha, beta, active, trials}]}]`. `read` scope.
- `PATCH /campaigns/{id}` (`operate`): `name`, `icp_description`, `value_prop`,
  `sender_persona`, `daily_cap`. Re-embed **only** when `icp_description` changes. Status
  is not editable here (activate/pause remain the only transitions).
- `PATCH /campaigns/{id}/steps/{step_id}` (`operate`): `wait_days` only — safe anytime
  (read at scheduling time, affects future scheduling only). Structural changes
  (`POST`/`DELETE` step) allowed **only while the campaign has zero enrollments** → 409
  otherwise (enrollments index into steps by `current_step`).
- `PATCH /campaigns/{id}/variants/{variant_id}` (`operate`): `name`/`active` always;
  `skeleton` only while trials == 0 → 409 with "clone as new variant" guidance otherwise
  (see open question 1).
- **Server-side skeleton validation** on variant create/edit: placeholders must be a
  subset of the 6 known slots (422 listing unknown names). `slot_schema` becomes optional
  on `VariantCreate` and is auto-derived from the placeholders actually used (column kept;
  no migration — see open question 2).

### Phase 2 — Web: create flow

- `/campaigns/new`: form for name, ICP description, value prop, persona (name, title,
  company, calendly), daily cap, and a steps editor (ordered wait_days list, default
  `[0, 3, 4]` matching the API default). Submits via the existing POST. Redirects to the
  new detail page.

### Phase 3 — Web: detail + builder page

- `/campaigns/[id]`: campaign fields editable in place; steps with wait_days; variants
  grouped per step showing name, α/β/trials/active, and the skeleton.
- **Skeleton editor:** textarea with slot-insert chips for the 6 valid placeholders;
  client-side validation mirrors the server rule (unknown placeholder = blocking error
  before save; missing `{{subject_hook}}`/`Subject:` line = warning). **Live preview**
  renders the skeleton client-side with canned sample fills + the campaign persona's
  signature — same substitution rule as `render_skeleton`, no LLM call.
- Variant with trials > 0: skeleton is read-only with a "clone as new variant" action
  (pre-fills the add-variant form). Existing activate/pause actions move onto this page.

### Phase 4 — Web plumbing

- `api.ts`: add `patch` helper + typed calls; extend `types.ts`; confirm/extend the
  `[...path]` proxy route for PATCH. Campaigns list page links each card to its detail
  page; empty state points at `/campaigns/new` instead of curl.

## Tests

- **API (pytest, the real coverage):** 401/403 scope checks per new endpoint; detail
  shape includes steps+variants; PATCH re-embeds only on `icp_description` change (mock
  embedder call-count); structural step change 409s once an enrollment exists; skeleton
  edit 409s once trials > 0; unknown placeholder 422s on create and edit; `slot_schema`
  auto-derivation; existing suite stays green, 0 skipped.
- **UI:** manual QA of the golden path (create → add variants → preview → activate) via
  the browse tooling. No JS test infra exists; adding one means touching `package.json`,
  which is an ask-first change — not doing it silently in this epic.

## Docs (definition of done)

- README: campaign creation section rewritten UI-first (curl moves to an API appendix).
- No new config knobs. No migration (no schema change under the recommended options).

## Open questions (⛔ decide before implementation)

1. **Variant edit policy once an arm has trials.** Recommend: block skeleton edits,
   offer clone-as-new-arm (fresh α=β=1, old arm can be deactivated). Alternative —
   edit + reset posterior — destroys measured history silently.
2. **`slot_schema` column.** Recommend: keep column, auto-derive server-side (no
   migration, API stays compatible). Alternative: drop it in a follow-up migration.
3. **Detail shape.** Recommend: expand `GET /campaigns/{id}` additively. Alternative:
   separate `/campaigns/{id}/detail` endpoint.
