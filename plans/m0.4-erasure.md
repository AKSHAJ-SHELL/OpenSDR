# Plan — Epic M0.4: GDPR erasure cascade (C2)

**Branch:** `m0.1-auth` (M0 line) · **Status:** approved by human 2026-07-21 (Q1 ordered deletes; Q2 substring scrub; Q3 KEEP audit data → anonymize instead of delete) · **Roadmap:** M0.4 · **Finding:** C2

## Goal

`DELETE /leads/{id}/erase` becomes a true multi-store erasure: after it runs, no store
holds data about the person — except the suppression entry, which must survive (it IS
the do-not-contact record). Erasing a lead with history must work (today it raises
IntegrityError the moment enrollments exist).

## Current state (verified in code)

- `erase_lead` (`compliance/suppression.py:48`) does `db.delete(lead)` + suppress. With
  any enrollment present this violates the `enrollments.lead_id` FK — **the endpoint is
  broken for every lead that was ever enrolled** (confirmed by FK layout; no ON DELETE
  anywhere in `models.py`).
- Stores holding lead-derived data (full audit):

| Store | What it holds | Today on erase |
|---|---|---|
| `leads` | name, email, title, linkedin | deleted (when FK allows) |
| `enrollments` | lead_id link | **orphaned/FK error** |
| `messages` | outbound bodies (greet the person by name) + **inbound reply text (prospect-authored PII)** | untouched |
| `unsubscribe_tokens` | `lead_email` column | untouched |
| `review_queue.payload` | JSONB: generated slots naming the person; classification rows store `"from": <lead email>` | untouched |
| `audit_log` | enrollment-linked state history + detail JSONB | untouched |
| `companies.research_brief` | JSONB brief — **may name the person** (e.g. scraped team/news pages) | untouched |
| Celery/Redis | task args are **IDs only** (verified `tasks.py`); result backend stores ints/None | no PII by design |
| `suppression_list` | the email + reason | **kept — by design** |
| `companies.embedding` / `icp_embedding` | company/campaign-level vectors, no person data | kept (not personal data) |

- Unmatched inbound email is never stored (`pipeline.py:44-46` returns before insert),
  so every `messages` row is reachable via `enrollment_id` — no orphan-PII search needed.
- Slack "interested" notifications already sent live in Slack — an external system
  outside erasure scope; documented, not handled.

## Design

### 1. Ordered explicit deletes (no schema change)

`erase_lead` becomes a single transaction, ordered by FK dependency:

1. collect `enrollment_ids` for the lead, and `message_ids` under those enrollments
2. delete `review_queue` rows referencing those enrollments **or** messages
3. **anonymize** `audit_log` rows referencing those enrollments (human decision: keep
   the data) — set `enrollment_id = NULL` (column is nullable) and scrub the `detail`
   JSONB with the same identifier scrub as the brief. With the enrollment gone and no
   identifiers in `detail`, the rows no longer relate to an identifiable person —
   anonymized data is outside GDPR scope, and the aggregate history survives.
4. delete `messages` under those enrollments
5. delete `enrollments`
6. delete `unsubscribe_tokens` where `lead_email == email`
7. **scrub the company research brief** (below) — the company row itself stays
8. delete the `leads` row
9. `suppress(email, reason="gdpr")` — the one record that must survive

Explicit ordered deletes over `ON DELETE CASCADE` (roadmap allows either): the
erasure semantics stay visible and testable in one function, no migration is needed,
and the FK constraints keep protecting against *accidental* lead deletion everywhere
else — only the GDPR path gets deletion power. (Cascade alternative noted for the
gate; flipping later is a small migration.)

### 2. Research-brief scrub (person mentions out, company facts stay)

`scrub_brief(brief: dict, identifiers: list[str]) -> tuple[dict, bool]` in
`compliance/suppression.py`: recursively walk the JSONB; in every string, replace any
case-insensitive occurrence of an identifier with `[redacted]`. Identifiers: the
email address (always), the full name, and first/last name individually when length
≥ 3 (skips initials; false positives just redact a word in a cached brief — cheap;
false negatives retain PII — expensive). Structure is preserved so the scrubbed dict
still validates as `ResearchBrief`. The cache timestamp is left alone deliberately:
forcing a refetch could re-scrape a team page that names the person again.

### 3. Queued-task safety (verify, not build)

Celery payloads are IDs; after erasure every task path already no-ops
(`db.get(...) is None` → return). This is asserted by test, making "a queued send
cannot resurrect an erased lead" a tested property rather than an assumption.

### 4. API / docs

- Endpoint unchanged (`DELETE /leads/{id}/erase`, admin scope, 204).
- README compliance section: state precisely what erasure covers (the table above) and
  that the suppression entry survives as the do-not-contact record. Erase UI stays in
  M1.3 per roadmap.

## Tests (`tests/e2e/test_erasure.py` + unit scrub tests)

1. **Regression:** lead with an enrollment → erase → **no IntegrityError** (today's bug,
   captured first).
2. **The zero-rows sweep:** build a lead with *full* history — enrollment, outbound +
   inbound messages, review-queue items (both kinds), audit rows, unsubscribe token,
   a research brief naming the person → erase → assert **zero rows** referencing the
   lead across messages/enrollments/review_queue/unsubscribe_tokens/leads; audit rows
   SURVIVE but with `enrollment_id IS NULL` and no identifiers in `detail`; brief no
   longer contains name/email; company row + company facts still present.
3. **Suppression survives and blocks re-import:** post-erase, `is_suppressed` is true and
   a CSV re-import of the same address is refused (existing import gate).
4. **Queued-task no-op:** call `generate_and_send` / `research_enrollment` /
   `enrich_lead` with the erased IDs → no exception, no send, no rows created.
5. **Scrub unit tests:** name in `what_they_do` / `trigger_events.claim` /
   `evidence_quotes`; email; case variations; short-name (< 3 chars) skipped; brief
   with no mention → unchanged (returns `changed=False`).
6. **Multi-lead isolation:** two leads at the same company → erasing one leaves the
   other's rows and the shared company untouched.

Suite ends green, 0 skipped, Postgres up. Adversarial debt: erasure is send-path
adjacent; the queued-task no-op test doubles as the §3.3-style safety case.

## Open questions for approval

1. **Ordered deletes vs `ON DELETE CASCADE` migration** — I propose ordered deletes
   (reasoning above).
2. **Scrub rule** — replace identifier substrings (email, full name, first/last ≥ 3
   chars, case-insensitive) with `[redacted]`, keeping the rest of the brief. Stricter
   alternative: null the whole brief when any identifier is found (loses company facts
   the roadmap says may stay). I propose the substring scrub.
3. **Audit history is deleted wholesale** for the erased lead's enrollments (FK order
   forces it anyway). GDPR wants it gone; you lose the state-transition history for
   that lead. Confirm.
