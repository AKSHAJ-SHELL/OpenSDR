# Plan — Epic M0.2: Alembic migrations (D1)

**Branch:** `m0.1-auth` (continues the M0 line) · **Status:** awaiting approval · **Roadmap:** M0.2 · **Finding:** D1

## Goal

Replace `Base.metadata.create_all` as the prod schema path with Alembic migrations.
Generate a baseline from the current models (which now include M0.1's `api_keys`), make
`init_db()`'s `create_all` a dev/test-only convenience, and require every future
model-touching epic to ship a migration. Prove upgrade→head and downgrade round-trip
against a fresh Postgres.

## Current state (verified in code)

- No Alembic anywhere (`no alembic dep`, no `alembic/` dir, no `alembic.ini`).
- `craftsman/core/db.py:52 init_db()` does `CREATE EXTENSION IF NOT EXISTS vector` then
  `Base.metadata.create_all(engine)`.
- Callers of `init_db()`: **API lifespan** (`api/app.py:16` — the prod path), plus
  `scripts/seed_demo.py`, `scripts/e2e_demo.py`, and `craftsman/create_key.py` (all dev).
- Tests build schema directly: `tests/conftest.py:45-46` `drop_all` + `create_all`.
- Models (`craftsman/core/models.py`) use pgvector `Vector(1024)`, `JSONB`, `UUID`,
  `server_default=text("now()")`. The `vector` extension must exist **before** any table
  with a `Vector` column is created.
- No CI at all (no `.github/workflows`).

## Design

### 1. Introduce Alembic

- Add `alembic>=1.13` to `pyproject.toml` **runtime** dependencies (migrations run at
  deploy, not just in dev). ⚠️ Needs `pip install -e .` — **approval item #1** (working
  agreement: ask before editing `pyproject.toml`).
- `alembic init craftsman/migrations` (migrations live inside the package so they ship in
  the Docker image). Wire `migrations/env.py` to:
  - `target_metadata = craftsman.core.models.Base.metadata`
  - the URL from `get_settings().database_url` (not a hardcoded `alembic.ini` URL), so one
    source of truth.
  - `compare_type=True` and `compare_server_default=True` for faithful autogenerate.
  - import `pgvector.sqlalchemy` so autogenerated scripts can reference `Vector`.
- `alembic.ini` at repo root with `script_location = craftsman/migrations` and a
  placeholder URL (overridden by `env.py`).

### 2. Baseline migration

- Autogenerate `0001_baseline` from the live models, then **hand-verify** it because
  autogenerate has two known blind spots here:
  - **pgvector extension:** prepend `op.execute("CREATE EXTENSION IF NOT EXISTS vector")`
    to `upgrade()` (and a matching drop is *not* added on downgrade — dropping a shared
    extension is unsafe; downgrade just drops the tables).
  - **`Vector` columns / import:** ensure `from pgvector.sqlalchemy import Vector` is in
    the script and the columns render as `Vector(1024)`.
- The baseline includes **every current table**, notably M0.1's `api_keys` (so a fresh DB
  built from migrations is identical to one built from `create_all`).

### 3. `init_db()` behaviour change

- **API (prod path):** the lifespan runs `alembic upgrade head` programmatically
  (`alembic.config.Config` + `command.upgrade`) via a new `run_migrations()` in
  `craftsman/core/db.py`. This keeps the "one `docker compose up`" story — schema is
  applied on startup, idempotently, through migrations. (Noted caveat: at multi-replica
  scale you'd split this into a one-shot migrate job; single-node default races nothing.)
- **`init_db()` keeps `create_all`** but is now called **only** by dev/test/demo code
  (`seed_demo`, `e2e_demo`, `create_key` bootstrap, and tests). The prod entrypoint no
  longer calls it. No fragile env-sniffing — the caller picks the path.
  - Alternative considered: env flag on `init_db`. Rejected — caller-choice is clearer.
- `create_key` bootstrap currently calls `init_db()` so the first key works before the API
  starts; switch it to `run_migrations()` so bootstrap uses the real schema path too.

### 4. Docker / compose

- No command change needed if the lifespan migrates. Optionally document that
  `alembic upgrade head` can be run manually. Keep localhost binds.

## Tests

`tests/e2e/test_migrations.py` (needs Postgres; consistent with the suite):

1. **Upgrade empty → head builds the expected schema.** Spin up a throwaway DB
   (`craftsman_migtest`), run `command.upgrade(cfg, "head")`, assert the table set matches
   `Base.metadata.tables` (names + columns), and that `api_keys` and a `Vector` column
   table both exist.
2. **Downgrade round-trips.** `upgrade head` → `downgrade base` (drops all tables) →
   `upgrade head` again succeeds. (With one migration, "one step" == base; the test also
   asserts a clean re-upgrade.)
3. **No-drift guard (the high-value one).** After `upgrade head`, run Alembic autogenerate
   in `--check` style (`compare_metadata`) and assert **zero** diffs between models and
   migrations. This fails CI the moment someone edits a model without a migration — the
   enforcement the roadmap asks for.
4. The existing fast test fixture keeps using `create_all` (speed); migrations get their
   own dedicated DB so the two paths don't interfere.

**CI:** no workflow exists today. **Approval item #2:** add a minimal
`.github/workflows/ci.yml` (Postgres service + `pip install -e ".[dev]"` + `pytest`) so
the migration round-trip runs in CI, or defer CI setup to a later ops epic and rely on
local `pytest` for now. I propose adding the minimal workflow.

Suite must end green, 0 skipped, Postgres up.

## Out of scope

- Data migrations / backfills (none needed — additive baseline). Multi-tenant `org_id`
  columns → M5.1. Splitting migrate into its own job → ops epic.

## Open questions for approval

1. **Add `alembic` as a runtime dep** (pyproject edit + `pip install`). Proposed: yes.
2. **Run migrations in the API lifespan** vs. a separate migrate step. Proposed: lifespan,
   to preserve one-command deploy (with the documented multi-replica caveat).
3. **Add a minimal GitHub Actions CI workflow** now, or defer. Proposed: add it (the
   roadmap explicitly names a CI job running migrations on fresh Postgres).

## Implementation order

1. Add `alembic` dep, `alembic.ini`, `alembic init`, wire `env.py` to Settings + Base +
   pgvector. `pip install -e ".[dev]"`.
2. Autogenerate + hand-verify `0001_baseline` (extension op, Vector import); confirm a
   fresh DB from migrations == models.
3. `run_migrations()` in `db.py`; API lifespan + `create_key` switch to it; `init_db`
   stays for tests/demos.
4. `tests/e2e/test_migrations.py` (upgrade / downgrade / no-drift) green.
5. Optional `.github/workflows/ci.yml`; README/knobs note that schema changes ship a
   migration.
